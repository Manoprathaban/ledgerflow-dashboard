# API documentation

This document defines the Ledger backend request payloads, response shapes, validation rules, and error semantics.

Related design docs:
- [ASSUMPTIONS.md](ASSUMPTIONS.md)
- [schema-design.md](backend/docs/schema-design.md)
- [frontend-design.md](backend/docs/frontend-design.md)

## Conventions

- Base path: `/api/v1`
- The interactive OpenAPI documentation is available at `/docs`; the
  alternative ReDoc view is at `/redoc`, and the OpenAPI JSON is at
  `/openapi.json`.
- All account, transaction, and transfer endpoints require
  `Authorization: Bearer <Supabase access token>`. The API validates the token
  with Supabase Auth; the authenticated Supabase user is the tenant.
- Every account and transaction response is restricted to that user. A user can
  transfer only between accounts they own.
- Resource identifiers use UUIDs (`uuid` format).
- Monetary values are serialized as decimal-safe strings with exactly two fractional digits, for example `"1250.00"`, never as floats. Requests may provide one or two fractional digits.
- Account names and descriptions are trimmed. Reference IDs are trimmed and case-folded before storage; reference uniqueness is case-insensitive.
- Timestamps are generated by the server and returned in ISO 8601 UTC format, for example `2026-10-26T12:00:00Z`.
- All list endpoints support pagination and return a consistent envelope. Lists are ordered newest first by `created_at DESC, id DESC`.
- Pagination is 1-indexed. `page_size` defaults to `10` and is limited to `100`; invalid values return `422`. Empty result sets have `total_pages: 0` and `page: 1`.

## Authentication quickstart

Sign in through the application or Supabase Auth to obtain a user access token.
Send that token with every protected API request:

```http
Authorization: Bearer <SUPABASE_ACCESS_TOKEN>
Accept: application/json
Content-Type: application/json
```

For example, list the signed-in user's accounts:

```sh
curl "https://<API_HOST>/api/v1/accounts?page=1&page_size=10" \
  -H "Authorization: Bearer <SUPABASE_ACCESS_TOKEN>" \
  -H "Accept: application/json"
```

Use the deployed backend host in place of `<API_HOST>` (locally,
`http://localhost:8000`). Never put a Supabase service-role key or database
credentials in frontend code. The backend must be configured with
`SUPABASE_URL` and `SUPABASE_ANON_KEY` so it can validate user tokens.

## Endpoint overview

| Method | Path | Purpose | Authentication |
| --- | --- | --- | --- |
| `GET` | `/health` | Liveness check | No |
| `GET` | `/api/v1/accounts` | List/search accounts | Required |
| `POST` | `/api/v1/accounts` | Create an account | Required |
| `GET` | `/api/v1/accounts/{account_id}` | Get an account | Required |
| `GET` | `/api/v1/accounts/{account_id}/balance` | Get current balance | Required |
| `GET` | `/api/v1/accounts/{account_id}/transactions` | List account transactions | Required |
| `POST` | `/api/v1/accounts/{account_id}/transactions` | Create a credit or debit | Required |
| `GET` | `/api/v1/transactions` | List transactions across owned accounts | Required |
| `GET` | `/api/v1/transactions/{transaction_id}` | Get a transaction | Required |
| `POST` | `/api/v1/transfers` | Transfer funds between owned accounts | Required |

The `/health` endpoint confirms that the API process is serving requests; it
does not verify database connectivity.

## Shared response envelope

### Success response shape

```json
{
  "items": [],
  "page": 1,
  "page_size": 10,
  "total": 0,
  "total_pages": 0
}
```

### Error response shape

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request payload is invalid.",
    "details": [
      {
        "field": "amount",
        "issue": "Amount must be greater than zero."
      }
    ]
  }
}
```

### Standard HTTP status codes

- `200 OK`: successful read
- `201 Created`: successful creation
- `401 Unauthorized`: missing, invalid, or expired Supabase access token
- `503 Service Unavailable`: Supabase Auth is not configured or cannot validate the token
- `404 Not Found`: resource not found
- `409 Conflict`: duplicate reference, insufficient balance, or balance limit exceeded
- `422 Unprocessable Entity`: malformed JSON, invalid UUID, query parameter, or request field
- `500 Internal Server Error`: unexpected backend failure

Error `code` values include `AUTHENTICATION_REQUIRED`, `AUTHENTICATION_UNAVAILABLE`, `VALIDATION_ERROR`, `ACCOUNT_NOT_FOUND`, `TRANSACTION_NOT_FOUND`, `DUPLICATE_REFERENCE`, `INSUFFICIENT_BALANCE`, `BALANCE_LIMIT_EXCEEDED`, and `INTERNAL_ERROR`. `details` is omitted when no field-specific information applies and is otherwise an array of `{ "field": string, "issue": string }` entries. All API errors use the error envelope above. FastAPI's default validation error body is translated to this envelope; unexpected `500` responses do not disclose stack traces or database details.

## Accounts

### `POST /api/v1/accounts`

Create a new account.

#### Request

```json
{
  "name": "Alice Johnson"
}
```

#### Validation

- `name` is required.
- `name` is trimmed before validation.
- `name` must be between 1 and 200 characters.
- Duplicate account names are allowed unless product requirements explicitly forbid them.

#### Success response: `201 Created`

```json
{
  "id": "5e9f8eb4-9831-4d0a-b9b0-9ff5f41d6722",
  "name": "Alice Johnson",
  "balance": "0.00",
  "created_at": "2026-10-26T12:00:00Z"
}
```

#### Error examples

- `422 Unprocessable Entity`: missing or blank `name`

### `GET /api/v1/accounts`

List accounts with pagination and search.

#### Query parameters

- `search` (optional): case-insensitive text search over account name and account id
- `page` (optional, default `1`): integer greater than or equal to `1`
- `page_size` (optional, default `10`): integer from `1` through `100`

Results are ordered by `created_at DESC, id DESC`.

#### Success response: `200 OK`

```json
{
  "items": [
    {
      "id": "5e9f8eb4-9831-4d0a-b9b0-9ff5f41d6722",
      "name": "Alice Johnson",
      "balance": "1250.00",
      "created_at": "2026-10-26T12:00:00Z"
    }
  ],
  "page": 1,
  "page_size": 10,
  "total": 1,
  "total_pages": 1
}
```

An empty result returns `items: []`, `total: 0`, `total_pages: 0`, and `page: 1`.

### `GET /api/v1/accounts/{account_id}`

Fetch one account by identifier.

#### Success response: `200 OK`

```json
{
  "id": "5e9f8eb4-9831-4d0a-b9b0-9ff5f41d6722",
  "name": "Alice Johnson",
  "balance": "1250.00",
  "created_at": "2026-10-26T12:00:00Z"
}
```

#### Error

- `404 Not Found` if the `account_id` does not exist
- `422 Unprocessable Entity` if `account_id` is not a valid UUID

### `GET /api/v1/accounts/{account_id}/balance`

Return the current net balance for a single account.

#### Success response: `200 OK`

```json
{
  "account_id": "5e9f8eb4-9831-4d0a-b9b0-9ff5f41d6722",
  "balance": "1250.00"
}
```

#### Errors

- `404 Not Found`: account does not exist
- `422 Unprocessable Entity`: `account_id` is not a valid UUID

## Money transfers

### `POST /api/v1/transfers`

Transfer funds between two accounts. The source debit, destination credit, and
both account balance updates run in one database transaction. If either account
is missing, funds are insufficient, or any database operation fails, none of
the transfer is committed.

#### Request

```json
{
  "source_account_id": "5e9f8eb4-9831-4d0a-b9b0-9ff5f41d6722",
  "destination_account_id": "47d65b2d-e0c1-4a43-92a5-b79da56f4c10",
  "amount": "30.00",
  "description": "Monthly savings"
}
```

The source and destination must be different existing accounts. The amount is
a positive decimal string with at most two fractional digits. The service locks
both account rows in a consistent order to prevent overdrafts and deadlocks.
Both accounts must belong to the authenticated user. A durable transfer row,
its debit and credit entries, and the balance updates are committed in one
database transaction; the database also enforces that both accounts share the
same owner.

#### Success response: `201 Created`

The response contains the transfer identifier, both immutable ledger entries
(one debit and one credit), and the resulting balance for each account.

```json
{
  "transfer_id": "7e6d5f4c-3b2a-1908-7f6e-5d4c3b2a1908",
  "source_transaction": {
    "id": "8ec6d6ca-2c2a-4abc-89a3-fafee1a6d15c",
    "account_id": "5e9f8eb4-9831-4d0a-b9b0-9ff5f41d6722",
    "type": "debit",
    "amount": "30.00",
    "description": "Transfer to Savings: Monthly savings",
    "reference_id": "transfer-7e6d5f4c3b2a19087f6e5d4c3b2a1908-debit",
    "created_at": "2026-10-26T12:15:00Z"
  },
  "destination_transaction": {
    "id": "c1b2a394-8576-4d0a-b1c2-d3e4f5061728",
    "account_id": "47d65b2d-e0c1-4a43-92a5-b79da56f4c10",
    "type": "credit",
    "amount": "30.00",
    "description": "Transfer from Checking: Monthly savings",
    "reference_id": "transfer-7e6d5f4c3b2a19087f6e5d4c3b2a1908-credit",
    "created_at": "2026-10-26T12:15:00Z"
  },
  "source_balance": "70.00",
  "destination_balance": "80.00"
}
```

#### Errors

- `404 Not Found`: either account does not exist or is not owned by the caller
- `409 Conflict`: source has insufficient funds, or destination balance would
  exceed the supported `NUMERIC(18, 2)` range
- `422 Unprocessable Entity`: malformed account UUID, same source and
  destination, invalid amount, or invalid description

### `POST /api/v1/accounts/{account_id}/transactions`

Create a credit or debit transaction for an account.

#### Request

```json
{
  "type": "debit",
  "amount": "125.50",
  "description": "Office supplies",
  "reference_id": "PO-2048"
}
```

#### Validation

- `account_id` is defined by the URL path.
- `type` must be either `credit` or `debit`.
- `amount` must be a decimal-safe string, greater than zero, with at most 16 integer digits and 2 fractional digits. Leading zeroes are not accepted except for the single integer digit `0`.
- `amount` should be validated using a decimal-safe parser; strings such as `"125.5"` and `"125.50"` are accepted, while malformed values are rejected.
- `description` is optional but trimmed before storage; if omitted or blank, the API stores `""`.
- `reference_id` is required, trimmed, and must contain 1-200 characters.
- `reference_id` must be unique within the same account.
- `reference_id` is case-folded before storage, so references that differ only by case conflict. The stored canonical value is returned in the response.
- A debit must not exceed the current account balance.
- The resulting balance must fit `NUMERIC(18, 2)`; a credit exceeding the maximum representable balance is rejected without writing either record.
- Balance update and transaction record insertion are atomic at the database transaction boundary.
- `description` is optional; omitted or blank values are stored as `""`. Non-empty descriptions are limited to 500 characters.

#### Success response: `201 Created`

```json
{
  "id": "8ec6d6ca-2c2a-4abc-89a3-fafee1a6d15c",
  "account_id": "5e9f8eb4-9831-4d0a-b9b0-9ff5f41d6722",
  "type": "debit",
  "amount": "125.50",
  "description": "Office supplies",
  "reference_id": "PO-2048",
  "created_at": "2026-10-26T12:15:00Z"
}
```

#### Error examples

- `404 Not Found`: account does not exist
- `409 Conflict`: duplicate `reference_id` for the same account
- `422 Unprocessable Entity`: invalid amount, type, or missing/invalid `reference_id`
- `409 Conflict`: debit exceeds available balance
- `409 Conflict`: resulting balance exceeds the supported `NUMERIC(18, 2)` range
- `422 Unprocessable Entity`: invalid `account_id` UUID

### `GET /api/v1/accounts/{account_id}/transactions`

Fetch transaction history for a single account.

#### Query parameters

- `type` (optional): `all`, `credit`, or `debit`
- `search` (optional): search by transaction id, description, or `reference_id`
- `start_date` / `end_date` (optional): ISO date strings (`YYYY-MM-DD`), inclusive
- `page` (optional, default `1`)
- `page_size` (optional, default `10`, range `1`-`100`)

Dates are interpreted in UTC. `start_date` includes midnight at the start of that UTC date; `end_date` includes the entire UTC date. An inverted date range returns `422`. An unknown account returns `404`.

#### Success response: `200 OK`

```json
{
  "items": [
    {
      "id": "8ec6d6ca-2c2a-4abc-89a3-fafee1a6d15c",
      "account_id": "5e9f8eb4-9831-4d0a-b9b0-9ff5f41d6722",
      "type": "debit",
      "amount": "125.50",
      "description": "Office supplies",
      "reference_id": "PO-2048",
      "created_at": "2026-10-26T12:15:00Z"
    }
  ],
  "page": 1,
  "page_size": 10,
  "total": 1,
  "total_pages": 1
}
```

### `GET /api/v1/transactions/{transaction_id}`

Fetch one immutable transaction by identifier. This endpoint is useful for the optional read-only transaction detail view.

#### Success response: `200 OK`

Returns a `TransactionResponse` object.

#### Errors

- `404 Not Found`: transaction does not exist
- `422 Unprocessable Entity`: `transaction_id` is not a valid UUID

There is no global `POST /api/v1/transactions` endpoint. Creation is account-scoped so the target account is explicit in the URL.

## Validation rules summary

- Account names must be non-empty after trimming.
- Transaction amounts are positive decimal strings with at most two decimal places.
- Duplicate `reference_id` values are rejected only within the same account.
- Reference comparisons are case-insensitive after trimming and case-folding.
- The same `reference_id` may be reused across different accounts.
- Debits reject if they would drive the account balance below zero.
- All writes are timestamped and immutable after creation.
- The schema enforces positive transaction amounts, non-negative stored balances, and per-account case-insensitive reference uniqueness. Transaction immutability is enforced by a database trigger and by not exposing update/delete endpoints.
- The database cannot enforce the cross-table equality between the cached account balance and the sum of ledger entries with a row-local `CHECK`; the service must keep both changes in one database transaction.

## Design notes for implementation

- Money should be modeled as decimal-safe strings in the API boundary and converted to integer minor units (`paise` / `cents`) internally for arithmetic where needed.
- The repository layer should use a single database transaction for each balance-changing write.
- Pagination should use stable ordering by `created_at DESC`, then by `id DESC` for deterministic results.
- Filter logic should combine text, account, type, and date constraints without requiring a client-side fallback.
- Account list and transaction list responses are paginated; do not compute global totals from the current page alone. The product must decide whether transaction summary cards are global or reflect active filters before adding an aggregate response.

## Implementation status

Account creation, retrieval, balance reads, paginated account search, transaction creation, transaction detail, filtered transaction histories, and account transfers implement this contract with PostgreSQL persistence and the documented error envelopes. Balance-changing operations are atomic. See the [backend README](backend/README.md) for current implementation and test status.
