# API contracts

This document defines the contract for the Ledger backend. It is the source of truth for the request payloads, response shapes, validation rules, and error semantics before backend implementation begins.

Related design docs:
- [schema-design.md](./schema-design.md)
- [frontend-design.md](./frontend-design.md)

## Conventions

- Base path: `/api/v1`
- Resource identifiers use UUIDs (`uuid` format).
- Monetary values are serialized as decimal-safe strings, for example `"1250.00"`, never as floats.
- The backend trims string fields before validation where relevant.
- Timestamps are generated by the server and returned in ISO 8601 UTC format, for example `2026-10-26T12:00:00Z`.
- All list endpoints support pagination and return a consistent envelope.

## Shared response envelope

### Success response shape

```json
{
  "items": [],
  "page": 1,
  "page_size": 10,
  "total": 0,
  "total_pages": 0
}
```

### Error response shape

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request payload is invalid.",
    "details": {
      "field": "amount",
      "issue": "Amount must be greater than zero."
    }
  }
}
```

### Standard HTTP status codes

- `200 OK`: successful read
- `201 Created`: successful creation
- `400 Bad Request`: malformed payload or invalid request
- `404 Not Found`: resource not found
- `409 Conflict`: duplicate or state conflict
- `422 Unprocessable Entity`: validation errors from schema parsing
- `500 Internal Server Error`: unexpected backend failure

## Accounts

### `POST /api/v1/accounts`

Create a new account.

#### Request

```json
{
  "name": "Alice Johnson"
}
```

#### Validation

- `name` is required.
- `name` is trimmed before validation.
- `name` must be between 1 and 200 characters.
- Duplicate account names are allowed unless product requirements explicitly forbid them.

#### Success response: `201 Created`

```json
{
  "id": "5e9f8eb4-9831-4d0a-b9b0-9ff5f41d6722",
  "name": "Alice Johnson",
  "balance": "0.00",
  "created_at": "2026-10-26T12:00:00Z"
}
```

#### Error examples

- `400` / `422`: missing or blank `name`

### `GET /api/v1/accounts`

List accounts with pagination and search.

#### Query parameters

- `search` (optional): case-insensitive text search over account name and account id
- `page` (optional, default `1`): 1-indexed page number
- `page_size` (optional, default `10`): page size, must be positive

#### Success response: `200 OK`

```json
{
  "items": [
    {
      "id": "5e9f8eb4-9831-4d0a-b9b0-9ff5f41d6722",
      "name": "Alice Johnson",
      "balance": "1250.00",
      "created_at": "2026-10-26T12:00:00Z"
    }
  ],
  "page": 1,
  "page_size": 10,
  "total": 1,
  "total_pages": 1
}
```

### `GET /api/v1/accounts/{account_id}`

#### Success response: `200 OK`

## Transactions

### `POST /api/v1/accounts/{account_id}/transactions`

Create a credit or debit transaction for an account.

#### Request

```json
{
  "type": "debit",
  "amount": "125.50",
  "description": "Office supplies",
  "reference_id": "PO-2048"
}
```

#### Validation

- `account_id` is defined by the URL path.
- `type` must be either `credit` or `debit`.
- `amount` must be a decimal-safe string, greater than zero, and represent at most two decimal places.
- `amount` should be validated using a decimal-safe parser; strings such as `"125.5"` and `"125.50"` are accepted, while malformed values are rejected.
- `description` is optional but trimmed before storage; if omitted or blank, the API stores `""`.
- `reference_id` is required, trimmed, and must be unique within the same account.
- A debit must not exceed the current account balance.
- Balance update and transaction record insertion are atomic at the database transaction boundary.

#### Success response: `201 Created`

```json
{
  "id": "8ec6d6ca-2c2a-4abc-89a3-fafee1a6d15c",
  "account_id": "5e9f8eb4-9831-4d0a-b9b0-9ff5f41d6722",
  "type": "debit",
  "amount": "125.50",
  "description": "Office supplies",
  "reference_id": "PO-2048",
  "created_at": "2026-10-26T12:15:00Z"
}
```

#### Error examples

- `404 Not Found`: account does not exist
- `409 Conflict`: duplicate `reference_id` for the same account
- `400` / `422`: invalid amount or missing `reference_id`
- `409 Conflict` or `400`: debit exceeds available balance

- `start_date` / `end_date` (optional): ISO date strings (`YYYY-MM-DD`), inclusive
- `page` (optional, default `1`)
- `page_size` (optional, default `10`)

#### Success response: `200 OK`

```json

    {
      "id": "8ec6d6ca-2c2a-4abc-89a3-fafee1a6d15c",
      "account_id": "5e9f8eb4-9831-4d0a-b9b0-9ff5f41d6722",

      "description": "Office supplies",

      "created_at": "2026-10-26T12:15:00Z"

  ],
  "page": 1,
  "page_size": 10,
  "total": 1,
  "total_pages": 1

```

### `GET /api/v1/transactions`

List transactions across all accounts with optional filters.

#### Query parameters

- `search` (optional): transaction id, account id, description, or `reference_id`
- `type` (optional): `all`, `credit`, or `debit`
- `account_id` (optional): filter to a specific account
- `start_date` / `end_date` (optional): ISO date strings (`YYYY-MM-DD`), inclusive
- `page` (optional, default `1`)
- `page_size` (optional, default `10`)

#### Success response: `200 OK`

```json
{
  "items": [
    {
      "id": "8ec6d6ca-2c2a-4abc-89a3-fafee1a6d15c",
      "account_id": "5e9f8eb4-9831-4d0a-b9b0-9ff5f41d6722",
      "account_name": "Alice Johnson",

      "amount": "125.50",

    }

  "page_size": 10,

  "total_pages": 1
```

## Validation rules summary

- Account names must be non-empty after trimming.
- Transaction amounts are positive decimal strings with at most two decimal places.
- Duplicate `reference_id` values are rejected only within the same account.
- The same `reference_id` may be reused across different accounts.
- Debits reject if they would drive the account balance below zero.
- All writes are timestamped and immutable after creation.
- The database layer must enforce immutability and balance invariants at the SQL level as well as in the service layer.

## Design notes for implementation

- Money should be modeled as decimal-safe strings in the API boundary and converted to integer minor units (`paise` / `cents`) internally for arithmetic where needed.
- The repository layer should use a single database transaction for each balance-changing write.
- Pagination should use stable ordering by `created_at DESC`, then by `id` for deterministic results.
- Filter logic should combine text, account, type, and date constraints without requiring a client-side fallback.

This contract is intentionally aligned with the Ledger frontend requirements and the existing schema foundation in the backend project.
